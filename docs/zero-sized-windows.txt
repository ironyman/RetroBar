❯ but why does it disappear                                                     

● Because Word itself destroys that window almost as fast as it created it —
  RetroBar isn't hiding it, the window's whole lifecycle (create → become
  foreground → get destroyed) happens in about the same instant, and the taskbar
  just faithfully mirrors each step.

  Concretely: TasksService.removeWindow() (TasksService.cs) is only ever called
  from a handful of places, and its log line is exactly "TasksService: Removed 
  window {hwnd} ({title})" with nothing else printed first. In the trace, that's
  what appears — no Cloak event, no RegisterTab, no CloseWindow-style "no
  response" message preceding it. That leaves one real candidate: the
  HSHELL.WINDOWDESTROYED case in ShellWinProc:

  case HSHELL.WINDOWDESTROYED:
      removeWindow(msg.LParam);
      break;

  This fires when Explorer's shell-hook mechanism (which RetroBar is registered
  for via RegisterShellHookWindow) sees the window's HWND actually get destroyed
  — a real WM_DESTROY, not a hide/cloak.

  So the sequence is:
  1. The Word add-in creates a throwaway, invisible, 0×0 top-level window
     (probably as some kind of internal focus-transfer or interop trampoline).
  2. That window briefly becomes the foreground window — which is what
     GetLastActivePopup handed RetroBar in makeForeground(), and what triggers
     HSHELL_RUDEAPPACTIVATED → RetroBar adds it as a task button.
  3. The add-in is done with it almost immediately and calls DestroyWindow on
     it, handing real focus to the actual Word document window.
  4. Explorer's shell hook reports that destruction, RetroBar's
     HSHELL.WINDOWDESTROYED handler calls removeWindow(), and the phantom button
     is pulled from the collection.

  All four of those steps land in the same handful of milliseconds (same log
  timestamp, often the same tick), which is why it reads as "pops up and
  disappears immediately" rather than a window that's actually hidden for a
  while.

  The fix I proposed still applies here: it's step 2 that's avoidable on
  RetroBar's side — if makeForeground() refuses to activate a 0×0/invisible
  popup returned by GetLastActivePopup and falls back to the real Handle,
  RetroBar never sets that helper window foreground in the first place, so it
  never gets picked up as a task button at all (steps 2–4 never happen). Want me
  to implement that guard?

❯ and why are we calling GetLastActivePopup

● Fetch(https://github.com/dremin/RetroBar/pull/353)
  ⎿  Received 240.1KB (200 OK)

● Good question — it's not incidental, it was added deliberately to fix a
  different bug (dremin/RetroBar#353, ManagedShell commit 1e84467, "Bring
  correct window to foreground").

  The problem it solves: if a window has a modal dialog open (e.g. Word's
  document window with a "Save As" or alert dialog up), Windows won't let the
  owner window take focus while its modal child is showing — that's how modality
  works. Before this change, RetroBar just called SetForegroundWindow(Handle)
  on the window you clicked. If that window had a modal dialog open, this would
  try to foreground the owner behind its own modal dialog — which either
  silently fails or looks broken (owner comes forward, dialog stays behind it,
  dialog doesn't actually get focus).

  GetLastActivePopup(Handle) asks Windows "what's the actual window that should
  get focus for this owner right now" — if there's a modal dialog up, it returns
  the dialog's hwnd; if not, it returns Handle itself unchanged. So clicking a
  task button correctly focuses the open "Save changes?" dialog instead of
  uselessly trying to activate the document behind it.

  Why it misfires here: GetLastActivePopup isn't scoped to currently visible
  popups — it returns whatever Windows last recorded as that owner's active
  popup, even if that popup is a stale, invisible, 0×0 helper window the add-in
  created and forgot about. Windows doesn't validate that for you; it just
  returns the last one it tracked.

  So the fix needs to keep calling GetLastActivePopup (that's load-bearing for
  the modal-dialog case) but reject what it returns when that popup isn't a
  real, visible, non-degenerate window — and fall back to Handle in that case,
  same as GetLastActivePopup itself falls back to Handle when there's no popup
  at all. Something like:

  private void makeForeground()
  {
      IntPtr hWnd = NativeMethods.GetLastActivePopup(Handle);
      if (hWnd != Handle && !IsGenuinePopup(hWnd))
          hWnd = Handle;
      ...
  }

  private static bool IsGenuinePopup(IntPtr hWnd)
  {
      if (!NativeMethods.IsWindow(hWnd) || !NativeMethods.IsWindowVisible(hWnd))
          return false;
      NativeMethods.GetWindowRect(hWnd, out var r);
      return r.Right > r.Left && r.Bottom > r.Top; // reject 0×0
  }

  That preserves the modal-dialog fix while filtering out the Word add-in's
  zero-size ghost popup. Want me to add this to ApplicationWindow.cs (and apply
  the same call sites — BringToFront, Restore, Maximize, DoClose, Move, Size all
  funnel through makeForeground)?

❯ what's the relationship between us calling GetLastActivePopup and word        
  creating that window?                                                         

  Searched for 1 pattern, read 1 file (ctrl+o to expand)
● They're two separate things, and mixing them up was my mistake in the earlier
  framing — let me be precise about what's actually established from the log vs.
  what's a source-side detail:

  What we know for certain:
  - Word/the add-in creates and destroys that invisible window. RetroBar never
    calls CreateWindow on anyone's behalf — it only ever queries and activates
    windows that already exist. So the window's existence is 100% Word's (or the
    add-in's) doing, not ours.
  - GetLastActivePopup is a pure, read-only query. It doesn't create, show, or
    activate anything. It just asks Windows: "of this window's owned popups,
    which one did Windows last record as active?" Windows maintains that
    bookkeeping on its own, updated any time an owned window becomes active for
    any reason — nothing to do with RetroBar.

  Where our call actually plugs in:
  Windows only lets you use SetForegroundWindow to steal focus — it won't let a
  background app pop something into existence as foreground on its own
  initiative in the general case. So for that invisible window to become the
  literal OS-wide foreground window (which is what makes the shell hook fire
  HSHELL_RUDEAPPACTIVATED and get a taskbar button drawn for it), someone has to
  explicitly call SetForegroundWindow(that hwnd).

  Looking at the two examples in the log, that "someone" isn't consistent:

  - In the first trace (0x2609FC), the phantom window becomes foreground before
    the real Word window does. That fits our code exactly: your click →
    BringToFront() → makeForeground() → GetLastActivePopup(Handle) happens to
    return that stray window (because Windows' bookkeeping says it's the "last
    active popup" for that owner) → we call SetForegroundWindow on it instead of
    the real window → it flashes into the taskbar → Word notices its scratch
    window wrongly has focus and immediately redirects to the real one. Here, we
    are the direct cause — our call is what promotes a dormant, forgotten
    window into real OS foreground.
  - In the third trace, the real Word window activates first, and the phantom
    shows up briefly after, with no second task-button click in between. That
    one isn't explained by our GetLastActivePopup call at all — nothing in
    RetroBar touches that window a second time. That has to be Word/the add-in
    calling SetForegroundWindow (or equivalent) on its own scratch window
    itself, as some internal side effect of its own activation handling.

  So the honest relationship is: GetLastActivePopup is a mechanism we use that's
  capable of surfacing this stray window and having us activate it on Word's 
  behalf — and the log shows that happening at least once — but it isn't the 
  only way this window gets activated. Word's add-in appears to have a genuine
  bug where a throwaway window it creates sometimes gets real OS focus,
  independent of us.

  Practically, this doesn't change the fix: guarding makeForeground() against
  degenerate (0×0/invisible) popups stops our contribution to the problem — the
  case where we're the one who promotes the stray window to foreground. It won't
  stop Word from doing it to itself in the other case, but RetroBar can't do
  anything about that half regardless (that's Windows correctly reporting a real
  foreground change Word itself initiated) — the shell-hook-driven phantom
  button would still flash for a tick either way. The guard is still worth
  adding since it's the one path where RetroBar is actively contributing to the
  glitch rather than just observing it.

  Want me to add it?

● Yes — that part is entirely Word's doing, and I can say that with more
  certainty than the activation side.

  RetroBar (nor ManagedShell underneath it) never calls DestroyWindow on any
  window it doesn't own. Grepping the whole codebase, the only DestroyWindow
  calls are on RetroBar's own internal hidden windows (TrayService's
  notification-icon host windows, ShellWindow.Handle). There's no code path
  anywhere that destroys another process's window — RetroBar has no mechanism to
  do that even if it wanted to (you can't DestroyWindow a handle owned by a
  different process/thread; only that thread can destroy its own window).

  So the removal is straightforwardly: Word's add-in creates that scratch 
  window, and Word's add-in tears it down itself — a plain DestroyWindow() call
  from inside Word's own process, almost immediately after creating it. That
  generates a genuine WM_DESTROY, which Explorer's shell-hook machinery (the
  same RegisterShellHookWindow mechanism any taskbar app registers for)
  broadcasts as HSHELL_WINDOWDESTROYED to every listening shell, RetroBar
  included.

  RetroBar's side of that is entirely passive — it's just this:

  case HSHELL.WINDOWDESTROYED:
      removeWindow(msg.LParam);
      break;

  removeWindow doesn't ask "was this window valid" or "should it have been
  added" — it just drops whatever ApplicationWindow instance has that handle out
  of the Windows collection, which is what makes the task button vanish from
  the WPF ItemsControl immediately.

  So to put the full lifecycle together now that all three questions are
  answered:
  1. Create — Word's add-in creates the invisible 0×0 window (its bug, not
     ours).
  2. Activate — it becomes the real OS foreground window either because we
     handed it real foreground via GetLastActivePopup + SetForegroundWindow
     (confirmed in one trace), or because Word activates it itself as a side
     effect of its own logic (the other trace) — RetroBar's shell hook sees this
     as HSHELL_RUDEAPPACTIVATED and adds a task button.
  3. Destroy — Word's add-in destroys the same window a moment later (its doing
     entirely), RetroBar's shell hook sees HSHELL_WINDOWDESTROYED and removes
     the button.

  RetroBar only actively contributes to step 2, and only in the case where our
  own GetLastActivePopup call is what surfaces the window. That's still the one
  piece worth guarding against — want me to add the fix now?

❯ so this isn't our problem? it's just word being weird and creating invisible

● Fair pushback — "not our problem" is too strong. Let me separate the two
  questions:

  Is Word creating a bogus 0×0 window our bug? No — that's genuinely Word/the
  add-in doing something weird internally. RetroBar can't stop Word from
  creating and destroying junk windows.

  Is showing a flash for it in the taskbar our bug? Yes, functionally — because
  the real Windows taskbar, watching the exact same OS-level events (it also
  gets HSHELL_RUDEAPPACTIVATED/foreground changes, or the modern equivalent),
  doesn't flash a button for this window. So whatever Explorer is doing
  differently is exactly the gap RetroBar should close.

  How does Explorer's taskbar avoid it? A couple of things, as far as this class
  of bug goes:

  1. It doesn't trust an activation event alone. Modern Explorer's taskband
     (Windows 8+) doesn't build its UI off the legacy HSHELL_* shell-hook
     messages at all — those are a compatibility shim kept around for
     third-party shells like RetroBar. Explorer itself uses the Immersive
     Shell's private window-list APIs (IApplicationViewCollection/DWM
     composition state), which carry more metadata and get to apply their own
     settle/eligibility logic before a view is considered "real." RetroBar, as a
     third-party shell, only has the legacy shell hook to work with, which is
     coarser — it reports every raw activation/creation as it happens, with no
     debounce.
  2. The obvious, generic filter: window size. A 0×0 window was never a
     legitimate on-screen application window a user could actually interact
     with. Explorer's window classification almost certainly excludes
     degenerate-rect windows outright.

  RetroBar's ApplicationWindow.CanAddToTaskbar (ApplicationWindow.cs) currently
  checks visibility, tool-window/owner/appwindow flags, and a shell-set
  "deleted" prop — but not window size. Every phantom instance in the log had
  rect=960,581,960,581 (zero area). Adding that one check closes this off at the
  earliest possible gate — TasksService.ShellWinProc's
  WINDOWACTIVATED/RUDEAPPACTIVATED case already bails out via !CanAddToTaskbar
  before ever calling addWindow, so a zero-size window would never get a button
  at all, regardless of whether it was RetroBar or Word that made it briefly 
  foreground. That's better than the makeForeground() guard alone, since it
  covers both causal paths we found (us activating it via GetLastActivePopup,
  and Word activating it on its own).

  Concretely:

  public bool CanAddToTaskbar
  {
      get
      {
          ...
          bool isDeleted = NativeMethods.GetProp(Handle, "ITaskList_Deleted") !=
  IntPtr.Zero;
          IntPtr ownerWin = NativeMethods.GetWindow(Handle,
  NativeMethods.GetWindow_Cmd.GW_OWNER);
          NativeMethods.GetWindowRect(Handle, out NativeMethods.Rect rect);
          bool hasArea = rect.Right > rect.Left && rect.Bottom > rect.Top;

          return isWindow && isVisible && hasArea && (ownerWin == IntPtr.Zero ||
  isAppWindow) && (!isNoActivate || isAppWindow) && !isToolWindow &&
  !isDeleted;
      }
  }

  I'd pair that with the earlier makeForeground() guard too
  (belt-and-suspenders, and it fixes the narrower "we're the one who promoted a
  stale popup" case even for windows that technically do have area but shouldn't
  be activated). But the size check in CanAddToTaskbar is the one that actually
  matches what you're seeing and would have prevented every instance in this
  log.

  Want me to add the CanAddToTaskbar size check (and optionally the
  makeForeground guard too)?

● It's detached for two separate reasons stacked on top of each other:

  1. That's just how git submodules normally work. When the outer RetroBar repo
  records a submodule, it pins ManagedShell to one exact commit SHA (a
  "gitlink"), not a branch name. git submodule update checks out that SHA
  directly, which is inherently a detached HEAD — there's no branch involved
  unless you make one yourself. This part is expected and not a problem by
  itself.

  2. But in this repo, that detached commit has actually drifted away from any 
  branch. Look at what git branch -v shows:

  * (HEAD detached from 078f233)   7dee207 Add SweepDeadWindows
    master                         078f233 [ahead 8, behind 8] Improve inactive
  fullscreen app detection
    remotes/mine/master            078f233 Improve inactive fullscreen app
  detection

  Your local master is in sync with mine/master (your fork on GitHub) at
  078f233. But HEAD is sitting on 7dee207, which is 8 commits ahead and 8 
  commits behind master — i.e. a genuinely separate line of history, not just
  "master plus a few commits." git log master..HEAD shows those 8 commits:

  7dee207 Add SweepDeadWindows
  5b22e08 Fix opening context menu on task button causes collapsed task group...
  d5d1c7b Fix restarting explorer break virtual desktop listening
  27e5ef5 Try to fix tray icons not appearing
  ... (4 more)

  That means at some point, commits were made directly on a detached HEAD in
  this submodule (this looks like it came out of earlier Claude Code sessions,
  going by the commit-message style) without ever cutting a branch for them.
  Each commit just kept advancing the detached HEAD, and the outer RetroBar
  repo's .gitmodules/gitlink got updated to point at wherever that detached HEAD
  ended up — which is why git submodule status shows 7dee207. Meanwhile master
  never moved, so it's now a stale, diverged branch that doesn't actually
  contain any of that work.

  Why this is worth fixing, not just living with: those 8 commits aren't
  reachable from any branch name right now. They only exist because the gitlink
  in the outer repo happens to point at them and because they're still in HEAD's
  history. If HEAD ever gets checked out to a different commit (another git 
  submodule update, a different clone, git gc eventually) without a branch
  anchoring 7dee207, those commits become much harder to find and are at real
  risk of being pruned.
